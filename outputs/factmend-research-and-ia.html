01 · POSITIONING

The proposition must go beyond native memory controls

Proposed category: agent memory governance. Primary user: privacy engineering lead at a B2B SaaS with persistent assistants across tenants. Champion: AI platform architect. Budget owner: privacy or security leadership.

Working promise: “Trace what agents remember. Correct it. Check what erasure changed.” Supporting copy should describe a proposed governance layer for mapping a fact across memory stores, derived indexes, caches and backup policies, with evidence and unresolved conditions presented together.

Native memory products already support important lifecycle operations. The website should show where Factmend might add value across a heterogeneous stack, and where a native provider may already be sufficient. A comparison page should use dated, operation-specific documentation rather than an unsupported wall of competitor checkmarks.

Candidate first pilot: Memory Signal, supported by Memory Review. Test a destination map, simulated selective erasure, read-after-delete checks, and a caveated receipt. Keep all five modules in the portfolio; choosing one pilot does not collapse the suite.

03 · PROPOSED ART DIRECTION

Three territories to explore before final branding

Recommended

Evidence Folio

Warm white, ink, muted aubergine and a restrained copper accent. An editorial canvas surrounds crisp evidence panels, source annotations and numbered chapters. One record opens into its history, then folds into a receipt.

Strongest balance of memorable storytelling and privacy-engineering credibility. Keep the UI sharp and contemporary so the paper metaphor never becomes nostalgic.

Boundary Atlas

Chalk, graphite and mineral green. Tenant and purpose boundaries become architectural lanes. A fact moves through explicit ports; allowed and denied retrieval paths are legible.

Best for an architecture-led narrative. Requires careful restraint to avoid the common abstract node-cloud appearance.

Revision Studio

Soft neutral surfaces, charcoal type and a controlled burnt-orange accent. Typographic before/after states lead the story: the old preference is revised, the source remains traceable, and destination statuses resolve.

Best for a product-led experience with less cinematic media. Needs original composition so it does not resemble a generic document editor.

These are proposed directions, not selected mockups or final tokens. The next design deliverable should be three comparable visual studies using the same hero, record, navigation and mobile crop. Choose the composition first, then create the logo, wordmark, favicon, two-family type system, palette, icon language and interaction rules.

Design principles specific to Factmend

  • The signature object is an evidence record, not a vault door, shield, brain, robot or floating orb.
  • Use refined type and hierarchy. Reserve large display text for a few narrative moments; keep data labels and technical copy comfortable to read.
  • Alternate editorial copy, a wide workbench, a destination map, product rows and a receipt. Avoid repeating a six-card grid throughout the page.
  • Use red for the persistent demo ribbon and destructive simulation context; use text and icons as well as color for every status.
  • Trust comes from specificity: sources, dates, scope, exclusions, failed checks and named evaluation criteria. Empty certification and customer-logo bands have no role here.

State model: learned → correction proposed → reviewed → superseded version → erasure requested → simulation completed with exceptions. Rejection, missing evidence, blocked destination and failed retrieval check are first-class states. Browser-only sample transitions are allowed; no real sends, billing, provider calls or infrastructure writes.

Assessment form

Step 1: work email, role, company and memory provider. Step 2: number of indexes/destinations, backup-window range including “unknown,” whether a privacy owner is identified, and whether sandbox access could be arranged later. Product interest is optional and contains all five modules. Ask for sandbox availability as a yes/no/unknown answer, never credentials or uploads. Optional interview opt-in is separate from explicit privacy consent.

Visible copy: “Do not submit customer records, prompts, logs, credentials or personal data about your users.” Publish the actual lead retention period and deletion route when the receiving system and responsible operator are known. An unconnected preview says “Preview complete — nothing sent”; a real success state only appears after confirmed delivery.

Measurement and validation

Plan the supplied events: landing_view, demo_open, demo_complete, pricing_view, form_start, form_submit, verified_signup and interview_booked. Keep synthetic demo events separate from real lead events. Use consent-aware measurement, campaign UTMs and server-side deduplication once a backend exists. Do not emit verified_signup from a browser-only form-success screen.

Advance product validation only when a privacy owner sponsors a funded sandbox pilot with security/DPA review, a complete destination map and named acceptance criteria. Define an acceptable retrieval-quality impact with that buyer. Pause when the gap beyond native controls cannot be reproduced or restoration/index limits cannot be evidenced.

07 · PRODUCTION PLAN

Build quality through explicit design and evidence

  1. Research and IA: this plan establishes the category, references, buyer journeys, route coverage and central story. Current vendor facts need rechecking when implementation starts.
  2. Visual exploration: create three comparable studies, then select the direction. Produce original logo/wordmark, monochrome/reverse variants, favicon/app icons, semantic colors, exactly two licensed font families, icon conventions and grid/spacing tokens.
  3. Product states: design C-012, the queue, correction, failed check and receipt before animating them. Establish the fixture data dictionary and chronology.
  4. Wireframes and motion storyboard: validate the homepage, module page, platform, pricing, intake, sign-in and narrow demo. Specify triggers, reverse behavior, static states and mobile versions.
  5. High-fidelity design: use Figma when producing editable design files; review typography, density, menus, forms, footer and every state at actual size. Image generation may support brand exploration, but must not substitute for genuine product UI or rendered screenshots.
  6. Implementation: React/TypeScript with multi-page routing; Next.js is a reasonable guide-aligned default. Keep semantic content available independently of animation. GSAP ScrollTrigger handles the bounded story; use gsap.matchMedia for responsive/reduced-motion variants. Start with native scroll; add Lenis only if it materially improves the tested experience.
  7. QA and delivery: test links, forms, keyboard, focus, status labels, zoom, touch, short screens, reduced motion, reset, fixture isolation and network behavior. Capture genuine 1440px and 390px renders of the hero, core workflow, pricing, demo boundary and form states. Record real results rather than predicted passes.
  8. Launch work: GitHub, Vercel, domain and real lead delivery follow when their destinations and credentials are available and launch is in scope. Research completion is separate from website completion and product validation.

Official implementation references: GSAP ScrollTrigger, responsive lifecycle and cleanup, accessible animation. Use current Core Web Vitals as acceptance targets: LCP ≤2.5 seconds, INP ≤200 milliseconds and CLS ≤0.1 at the 75th percentile, assessed separately for mobile and desktop. These are targets, not measurements of an unbuilt site. Google Web Vitals guidance.
