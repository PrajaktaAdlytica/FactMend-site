# Factmend: competitive evidence and website lessons

Research date: 8 October 2026. Research-stage concept, not a shipping product. Factmend replaces the provisional Recall Harbor brand in the supplied brief. The attached master guide was read in full; its architecture recommendations inform planning, while the concept brief controls claims and maturity.

## Decision

Lead with the investigation a privacy engineer must perform: **trace one fact, correct it, map its destinations, and inspect what a deletion test actually establishes**. Basic memory deletion, scoping, version history, and retention already exist in alternatives. Factmend's proposed value is coordinated evidence across a heterogeneous deployment; it remains a demand and technical hypothesis until tested against the buyer's actual native stack.

## Strong positioning and weak positioning

### Additional distinctions confirmed after Perplexity high research

- **Mem0 expiration is not deletion.** Its dedicated expiration documentation says expired records are hidden from normal search/list results, remain stored, and can still be fetched by ID. The delete operation is separate. The Platform also documents filtered, schema-driven exports. [Expiration semantics](https://docs.mem0.ai/platform/features/memory-expiration), [Export](https://docs.mem0.ai/platform/features/memory-export).
- **Supermemory API generations must be distinguished.** The extracted-memory v4 forget operation above is soft deletion. Current document/namespace workflows document permanent deletion with no recovery. That page does not independently prove every backup's treatment. Do not characterize all Supermemory deletion as soft deletion. [Current ingestion and deletion guide](https://supermemory.ai/docs/ingestion/add-memories).
- **Google conditional access has API boundaries.** The current IAM page states that multi-scope methods including `ListMemories` and `PurgeMemories` do not support IAM conditions and require an unconditional grant. Scope-based retrieval policies do not mean every administrative enumeration operation has identical constraints. [IAM limitations](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank/iam-conditions).

Recommended research-stage positioning: **Factmend is a proposed memory-governance workbench for privacy and platform teams. Map a fact across your agent stack, test correction and erasure, and review the evidence and remaining limits.**

Avoid: “first memory with deletion,” “all competitors lack governance,” “erase forever,” “fully compliant,” “zero leakage,” “guaranteed tenant isolation,” “verified integrations,” and “proven savings.” None is supported for Factmend.

Suggested public headline direction: **A fact changed. Did every memory?** Follow immediately with a concrete descriptor: “Explore a proposed governance layer for persistent agent memory—trace sources, review corrections, and inspect destination-by-destination erasure evidence.” CTA: **Map your memory deletion paths**. Secondary CTA: **Explore the synthetic demo**.

Preserve the five proposed modules from the brief (renaming only the company prefix): Factmend Memory Desk; Memory Review; Memory Proof; Memory Signal; Memory Report. Their unusual name-to-capability mapping remains as supplied. Use descriptive subtitles everywhere. They are five module hypotheses, not five live products or pricing tiers.

| [Google Memory Bank docs](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank) | Overview, API quickstart, setup, generation, retrieval, revisions, access controls | Give complex governance concepts separate readable explanations | Cloud provider scale, certifications, service guarantees or an oversized cloud-navigation system |

For the homepage's scroll narrative, show **one continuous record**, not a carousel of disconnected dashboards: C-012 preference → source/purpose/tenant scope → corrected version → propagation destinations → retrieval test → receipt with an explicit unresolved backup line. This is an original application of the brief, not a copied competitor composition.

## What the pilot must establish

1. Exact memory engine, API/product version, hosting region, tenant boundary, purpose policy, retention baseline, logs, source records, indexes, caches, exports and recovery copies.
2. A reproducible failure or evidence gap beyond the provider's native delete/update/TTL controls.
3. A named privacy owner, budget owner and acceptance criteria before calling a lead qualified.
4. Before/after retrieval evaluation, tenant isolation tests and explicit non-target controls; never treat an empty top-k result alone as physical erasure proof.
5. Destination-specific observations, attempted operations, failures, timestamps, retry windows and source of any backup policy statement.
6. A decision to advance only with a funded sandbox and reproducible incremental value; pricing remains the supplied hypothesis, not observed willingness to pay.

## Research limitations

Additional governance references: [Google scope-based IAM Conditions](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank/iam-conditions), [Zep policy-based access control](https://help.getzep.com/policy-based-access-control), and [Zep source traceability](https://help.getzep.com/source-traceability). These make a broad claim that incumbents lack governance particularly unsafe. Scope metadata and an enforced authorization boundary must be evaluated separately in an actual deployment.

No live vendor account, paid plan, infrastructure audit, benchmark run or buyer interview was performed. Documentation changes rapidly. Public documentation can establish stated semantics, but cannot validate a particular customer's configuration, contract, compliance position or deployment. Domain availability and trademark clearance for Factmend have not been assessed. No vendor comparison here establishes independent demand for Factmend.
