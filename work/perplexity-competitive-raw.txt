# Agent-memory governance: official-documentation evidence matrix

**As of October 8, 2026, Factmend’s strongest defensible position is per-destination verification of corrections and erasure—not a claim that memory products lack native delete.** Every named memory product below documents a way to remove at least some data. The harder problem is establishing *which* source, derived fact, shared summary, index, revision, export, or backup was affected, then recording what was actually checked. In particular, “expired,” “forgotten,” “invalidated,” and “deleted” have different documented meanings.[web:167][web:85][web:114][web:230]

**Reading rule:** “Unknown” means the cited primary documentation does not establish the stated outcome; it is **not** evidence that a feature or protection is absent. Product benchmark results are evidence of the vendor’s evaluation method, not independently verified governance or erasure results.

| Product / deployment | Tenant/user and purpose scoping | Provenance, history and correction | Retention / expiration | Delete granularity | Downstream, index and backup erasure caveats | Export / portability and evaluation |

| **Mem0 Platform / OSS** | Platform writes and filters use `user_id`, `agent_id`, `app_id`, `run_id` and metadata; the docs propose `app_id` for tenant separation and metadata categories for finer use. **Important:** default extraction attributes a fact to *either* user or agent, so filtering for both with `AND` can miss those facts. Treat purpose labels and application authorization as an implementation design, not a documented automatic purpose-policy engine.[web:17] | `update` changes memory text/metadata and adjusts indexes; the [history API](https://docs.mem0.ai/api-reference/memory/history-memory) documents `ADD`, `UPDATE`, `DELETE`, prior/new text and conversation `input`. Separately, Mem0 describes **ADD-only automatic extraction**: changed information can leave older facts alongside newer ones unless explicitly corrected or removed. Whether history remains retrievable *after* memory deletion is unknown from that API page.[web:158][web:157][web:19] | [`expiration_date`](https://docs.mem0.ai/platform/features/memory-expiration) is **not erasure**: “Nothing is deleted.” Expired records are normally omitted from `search`/`get_all`, but remain available through `get(id)` and optional expired-result retrieval. A later delete must be scheduled for a hard retention deadline.[web:167] | `delete(memory_id)`, `batch_delete` of up to 1,000 IDs, and filtered `delete_all` by entity or metadata are documented. The guide says to confirm the response and search again; wildcard scopes require care.[web:156][web:23] | The described architecture includes vector, graph/entity and SQL-history stores; the cited delete guide does **not** establish erasure timing or independent verification across every derived store or backup. Do not turn that uncertainty into a claim that native delete is absent. The history schema itself can contain old text and conversation input, making history handling an explicit diligence question.[web:157][web:156][web:19] | Platform has filtered, schema-driven [export jobs](https://docs.mem0.ai/platform/features/memory-export); OSS lacks that *Platform export feature*, although both have `get_all`. Downloadable exports expire after seven days. Mem0 publishes a reproducible evaluation framework for recall, latency and tokens; its published scores reflect the managed platform and are **not** erasure tests.[web:20][web:93][web:105] |
| **Google Vertex AI Agent Engine Memory Bank** | Memories carry an arbitrary scope, such as `{user_id, session_id}`; [`RetrieveMemories`](https://docs.cloud.google.com/agent-builder/agent-engine/memory-bank/fetch-memories) requires an **exact** scope match, and scope is immutable. Scope-key customization can constrain extraction topics—useful for intended-purpose design. Scope-based IAM Conditions exist, **but `ListMemories` does not support IAM Conditions** and requires an unconditional listing grant.[web:212][web:86][web:215] | Direct create/update/delete and generated consolidation are documented. Default-on immutable [`MemoryRevision`](https://docs.cloud.google.com/agent-builder/agent-engine/memory-bank/revisions) snapshots support inspection and rollback; generated revisions can show intermediate extracted memories and optional source-identifying labels. The page does **not** establish that revisions contain the complete source transcript. These are genuine native correction/history facilities.[web:33][web:89] | Memory TTL is optional: without configuration or a manual expiration, memories do not automatically expire; after configured expiration they become unavailable and are deleted. **Revision** TTL is separate and defaults to **365 days**; revisions can instead be disabled or assigned another TTL.[web:86][web:85] | Delete one memory by resource name. Criteria-based [`purge`](https://docs.cloud.google.com/agent-builder/agent-engine/memory-bank/quickstart-api) accepts system/metadata filters, offers a non-executing preview (`force=False`), and returns `purge_count`; Google illustrates `scope.user_id` purging. Generation may also remove contradictory memories.[web:214][web:32] | A deleted memory returns 404, **but its child revisions remain inspectable and rollback-capable for up to 48 hours** after parent deletion; the latest deletion revision has an empty fact. The cited Memory Bank pages do not establish backup erasure or downstream copies. A 404 therefore proves less than irreversible eradication.[web:85] | `ListMemories` and exact-scope retrieval support enumeration and application-managed extraction; a dedicated bulk-export guarantee is **unknown** from the cited pages. Google describes Agent Platform Example Store/Evaluation Service, but the Memory Bank overview gives no Memory Bank-specific erasure-evaluation workflow.[web:212][web:90] |
| **Zep managed Context Graphs, v3** | Project, user/thread and shared `graph_id` boundaries are documented. Zep advises deriving IDs from authenticated application state. Enterprise-only ABAC policies can restrict API-key actions and source classes using projected episode metadata; this is more specific than a mere marketing claim of “governance.” The application still authorizes external actions.[web:204][web:275][web:270] | Facts link to source episodes. `valid_at`/`invalid_at` describe a fact’s **derived temporal validity, not its truth or data-retention deadline**. New evidence can invalidate an old edge; an individual fact can be removed by deleting its edge. Source references and API/audit logs offer useful provenance surfaces.[web:202][web:180][web:265] | The reviewed v3 security and graph-deletion guides do **not** establish a universal memory TTL or backup-retention schedule. `expired_at` is the time Zep learned a fact was false—not proof that stored data expired.[web:180][web:275] | Documented APIs delete an edge, node, episode or thread; Zep also documents user and shared-graph deletion. This is **not** a product without native delete.[web:114][web:115] | Exceptionally concrete warning: deleting an episode **does not regenerate shared node names or summaries**, where episode information may remain; shared edges/nodes survive, a user entity node survives episode deletion, and deleting an invalidating episode does not revalidate its fact. Verify resulting graph and retrieved context, not just the episode response. Backup-specific erasure remains unknown from these guides.[web:114][web:275] | Search/list APIs expose graph material for application-managed extraction; a guaranteed complete, portable graph-export format is **unknown** from the reviewed pages. Zep’s [evaluation harness](https://help.getzep.com/evaluate-zep-for-your-use-case) scores context completeness and answer accuracy, not erasure. Enterprise governance claims should be distinguished from the specific ABAC, provenance and log mechanisms documented above.[web:180][web:201][web:270] |
| **Graphiti open source, self-operated** | `group_id` namespaces episodes and graph artifacts; operation and storage choices remain the operator’s responsibility. Zep explicitly distinguishes Graphiti’s **self-managed** governance from its managed service’s policies, logs and deployment controls.[web:6][web:200] | Episode-based provenance and temporal fact invalidation are documented. Graphiti CRUD exposes entity/edge reads and saves; these are graph operations, not an independently established end-to-end correction workflow for every application copy.[web:172][web:120] | A platform-wide retention/backup policy is **operator-defined or unknown** from the reviewed Graphiti guides; do not transfer Zep-managed policy claims to this deployment.[web:200] | CRUD documents entity/edge `delete`, `delete_by_uuids` and node `delete_by_group_id`; its MCP-server guide documents episode deletion and group management. Check the particular Graphiti version and backing driver used.[web:120][web:110] | Verify surviving linked nodes/edges and any external graph database, index and snapshots separately. Neo4j, a documented Graphiti backend, has restorable database backups; deleting from a live graph alone does not demonstrate a historical backup was changed.[web:178][web:145] | Query/CRUD access and operator-managed database migration are documented; a universal Graphiti portable export or governance-evaluation guarantee is **unknown** from the cited guides. The Zep managed evaluation harness should not be represented as a Graphiti-native erasure test.[web:120][web:200][web:201] |
| **Letta: legacy V1 memory and newer Agent SDK MemFS** | V1 memory blocks and passages are addressed by agent/block/passage IDs; blocks **can be shared across agents**. The newer Agent SDK stores agent-owned memory in git-backed MemFS and supports shared repositories. The [SDK comparison](https://docs.letta.com/v1-sdk) explicitly says V1 does **not** provide MemFS/git-tracked memory: do not combine the two histories into one claimed API.[web:61][web:134][web:245] | V1 block `value` updates **replace the whole value**; concurrent changes are last-write-wins. Developers can manage archival passages via SDK, while conversation search can retrieve original messages. Agent SDK MemFS edits become memory when committed and pushed. Purpose-tag governance and a V1 block-revision/undo API are **unknown** from these pages.[web:61][web:56][web:134] | No general memory TTL is established in the reviewed block, archival and MemFS guides. Local-mode state is the operator’s backup responsibility; signed-in agents can be cloud-backed.[web:61][web:56][web:242] | V1 APIs delete an archival passage or agent; deleting a block removes it from **all** attached agents, whereas detaching it from one agent **does not delete the block**. These are materially different erasure actions.[web:59][web:51][web:61] | Check all agents sharing a block, message history, attached folders/archives and the selected local/cloud or git backup arrangement before attesting erasure. The reviewed docs do not establish one operation that proves removal across those destinations.[web:61][web:56][web:134][web:242] | V1-era [AgentFile `.af`](https://docs.letta.com/v1-sdk/concepts/agent-file) import/export includes message history and blocks; the page says archival passages are **planned**, so do not promise their inclusion. Secrets export as `null`. Letta evals can grade block persistence, not cross-store deletion; Agent SDK git portability is a **different** mechanism.[web:237][web:127][web:134] |
| **Supermemory: v5 documents; distinct v4 extracted-memory APIs** | In v5, each call targets one URL-path `namespace`, with examples per user or organization/user; metadata filters also apply to search, list and profile. `taskType: "memory"` extracts facts/profile/graph, whereas `"superrag"` indexes chunks without those steps—an actual documented processing-purpose switch, **not** a documented authorization policy.[web:41][web:42] | v5 stable document IDs support incremental ingest; `documents.update()` replaces content and triggers full reprocessing. Search can attach a source document. **Separately, v4** `PATCH /v4/memories` creates a new extracted-memory version; `POST /v4/memories/list` returns history and `documentIds`. Do not silently treat these as v5 endpoints.[web:42][web:45][web:230][web:227] | Search normally excludes forgotten memories and those past `forgetAfter`; this establishes retrieval behavior, **not physical deletion**. The v4 list schema includes `forgetAfter` and `forgetReason`.[web:45][web:227] | v5 `documents.delete(namespace,{ids})` deletes specified documents and `namespaces.delete(namespace)` deletes the namespace’s content; its guide calls these permanent, unrecoverable deletes. In contrast, v4 `DELETE /v4/memories` **soft-deletes** an extracted memory (`isForgotten=true`, retained in the database); v4 semantic bulk-forget has preview and exact-ID modes.[web:42][web:230] | A v5 write can create chunks, embeddings, extracted facts, profile and graph links. The cited document-deletion guide calls deletion permanent but does **not** specify per-derived-artifact or backup erasure evidence. Conversely, v4 forgetting explicitly preserves the memory. Test both retrieval and derived-context surfaces; backup treatment remains unknown.[web:42][web:230] | v5 list/get provide application-managed enumeration; the v4 history endpoint exposes source IDs. A complete portable export guarantee is **unknown** from these pages. Vendor [MemoryBench](https://supermemory.ai/docs/memorybench/overview) evaluates ingest→search→answer accuracy, latency and tokens across providers, not privacy erasure.[web:41][web:227][web:229] |
| **Qdrant, self-hosted vector database** | Documented shared-collection tenancy uses a tenant payload field and **explicit query filter**; alternatives include dedicated/tiered shards. `is_tenant=true` improves storage organization; it is not a substitute for enforcing authenticated tenant/purpose filters in the application.[web:151] | Points carry IDs, vectors and payload; the cited point API permits retrieval/scroll. Source IDs, correction history and purpose labels must be modeled by the operator rather than assumed from the point API.[web:72] | An automatic per-memory retention policy is **unknown** from the reviewed point and multitenancy guides; implement and test the required schedule separately.[web:72][web:151] | [`points/delete`](https://qdrant.tech/documentation/manage-data/points/) accepts IDs **or a payload filter**. Mutations are asynchronous unless requested with `wait=true`; mere `acknowledged` is not `completed`. Retrieve by ID or scroll with the same filter to test the live collection.[web:72] | A [collection snapshot](https://qdrant.tech/documentation/operations/snapshots/) contains **all points and payloads** and can restore earlier state. There are APIs to delete individual collection or full-storage snapshots, but no cited guarantee that deleting live points scrubs existing snapshots, separately managed backups or exported files.[web:184] | Scroll/point retrieval and downloadable/restorable snapshots provide data movement. The pgvector-style recall benchmarks or application-level erasure evaluation are **not** established as Qdrant-native by these cited guides.[web:72][web:184] |
| **Weaviate, self-hosted vector database** | Multitenant collections allocate tenant shards; object deletion requires collection and tenant. Properties and filters can carry application purpose; the cited data model does not itself certify application-purpose authorization.[web:251][web:69] | Object update/delete exist. A built-in source-conversation provenance or correction-history record is **unknown** from the cited object/data guides; retain application source IDs if required.[web:69][web:251] | Object TTL is configurable, **but setting TTL alone does not delete objects**: the background deletion schedule is empty by default and must be enabled. Expired objects can be excluded from queries pending deletion.[web:251] | Delete by object ID or filter; delete a tenant to delete its shard and objects. **TTL deletion skips inactive/offloaded tenants until they become active**, a crucial verification condition.[web:69][web:251] | Backups include active and inactive tenants, but not offloaded tenant data. **There is no tenant-level restore**: restoring a backup restores its collection. Thus a deleted live tenant can remain in an earlier collection backup; verify backup inventory and restore policy separately.[web:250][web:251] | Collection/instance backups support migration, not tenant-only restore. A vendor-provided correction/erasure evaluation is **unknown** from the cited guides.[web:250] |
| **PostgreSQL + pgvector, self-hosted native/vector stack** | SQL tenant/user/purpose columns can be filtered; PostgreSQL row-level security can govern row access if enabled and configured. pgvector warns that approximate-index filtering occurs **after** index scan and recommends partitions or separate tables for tenant isolation of recall.[web:185][web:1] | Ordinary SQL `UPDATE`/`DELETE` and caller-defined provenance/history tables are available; pgvector does **not** supply an agent-source history schema in its cited README. Compare approximate search with exact search when evaluating recall.[web:1] | Memory-specific TTL is **not documented** in the cited pgvector README; retention is an application/database operations design.[web:1] | SQL `DELETE` targets rows; pgvector documents HNSW maintenance using `REINDEX INDEX CONCURRENTLY` then `VACUUM`. Verify relevant tables and query paths, not just vector search.[web:1] | PostgreSQL explains that updates/deletes do **not immediately remove old MVCC row versions**; ordinary `VACUUM` removes dead versions for reuse but is **not documented as secure wiping**. SQL dumps, file backups and archived WAL require their own retention/restore controls.[web:152][web:261][web:263] | `pg_dump` is a portable logical export; pgvector documents exact-versus-approximate recall checks. Neither constitutes native end-to-end agent correction or backup-erasure attestation.[web:261][web:1] |

## What Factmend should test—and what it should say

A credible control is a **destination ledger**, not a universal “delete succeeded” flag. For each source item, record authenticated tenant, user, permitted purpose, source/version ID, derived memory or graph IDs, destinations and backup policy. On correction or erasure, choose the *documented* operation appropriate to each destination; capture its completion state; then enumerate or retrieve using the same scope and check for the superseded fact in ordinary retrieval, source-linked artifacts and shared context. Qdrant’s `acknowledged` versus `completed`, Google’s purge preview/count, and Zep’s surviving shared summaries illustrate why an API response alone is insufficient.[web:72][web:214][web:114]

Report outcomes separately: **live readback verified**, **derived/shared context checked**, **revision or soft-forget window remains**, **historical backup subject to stated lifecycle**, and **unknown—not verified**. Never equate Mem0 expiration, Supermemory v4 forget, Zep temporal invalidation or Google’s deleted-memory 404 with proven destruction of every historical copy. Nor should Factmend claim those systems lack native deletion.[web:167][web:230][web:180][web:85]

| **Zep managed** | [help.getzep.com](https://help.getzep.com/overview): Quickstarts → SDK Reference → Governance → Graphiti, with v3 and v2 documentation indexes. | **Graphiti open source** | [Graphiti overview](https://help.getzep.com/graphiti/getting-started/overview) → core concepts/namespacing → working with data/CRUD → backend configuration. | **Letta** | [docs.letta.com](https://docs.letta.com/v1-sdk): distinguish legacy **V1 SDK** blocks/passages/API reference from **Agent SDK** → Memory → MemFS/shared memory; link AgentFile export and evals with their version context.[web:245][web:134][web:237] |

| **Self-hosted data layer** | [Qdrant multitenancy/points/snapshots](https://qdrant.tech/documentation/manage-data/multitenancy/); [Weaviate data objects/TTL/backups](https://docs.weaviate.io/weaviate/concepts/data); [PostgreSQL backup/VACUUM](https://www.postgresql.org/docs/current/backup.html).
